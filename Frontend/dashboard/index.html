          How items are ranked

          The 100-point priority score, explained

          The formula
          Score = In CISA KEV: 40 + AI severity (0-10) × 4 + Public PoC: 20 Max 100

          Items that share a CVE ID (the NVD record, its KEV entry, a GitHub advisory, a PoC) are scored as one story, so each gets the KEV and PoC points if any of them has them. Out-of-scope items score 0 and are not sent to the AI.

          Why 40 / 40 / 20

          The weights follow the three exploitation states used by SSVC: none, public proof of concept, and active. Active exploitation carries the most weight because a CISA KEV listing is confirmed evidence that attackers use the flaw. A public PoC carries half as much: it lowers the barrier to attack but does not prove anyone is using it. Practical severity carries the remaining 40, so within each exploitation state items are ordered by what an attacker gains.

          Official CVSS is not in the score. New records often have no CVSS yet, or a worst-case default, and CVSS describes technical severity rather than what matters for a test this week. It is still shown, and compared with the AI rating below.

          What a score means

          40 to 100: exploited in the wild

          Every CISA KEV item. A KEV item with severity above 5 outranks every item that is not in KEV. This is deliberate: exploited issues come first.

          20 to 60: public PoC, not in KEV

          Exploit code is public but no exploitation has been confirmed. Ordered by severity.

          0 to 40: no known exploitation

          Ranked on severity alone. A critical bug here can score 38: it is serious, but nobody has been seen using it yet.

          How the AI rates severity (0 to 10)

          Qwen 2.5 72B reads the title, product, CVE ID and the first 3,000 characters of the cleaned advisory, and rates practical attack impact with these bands:

          9 to 10, critical: unauthenticated RCE, authentication bypass, account takeover, root or kernel privilege escalation.
          7 to 8.9, high: SSRF, SQL injection with data exfiltration, intent hijacking, memory buffer overflow.
          4 to 6.9, medium: stored or reflected XSS, CSRF, constrained path traversal, information disclosure.
          0 to 3.9, low: local denial of service, memory leaks, flaws needing physical or restricted access.

          If the model is unreachable, a keyword fallback gives coarse ratings (9.5, 8, 6 or 3.5). Those are marked "heuristic_engine" and re-scored by the model on the next run.

          What is in scope

          Web and mobile testing targets only. Rules run in order: the source (PortSwigger and GitHub advisories are web; Android, Apple and Frida are mobile), out-of-scope words (printer, SCADA, PLC, UEFI, router firmware and so on), web and mobile CWE lists, then web and mobile keywords. Each item shows which rule placed it. Known limitation: some infrastructure and desktop advisories still pass the keyword rule, so check the scope reason when an item looks out of place.

          CVSS discrepancy flag (difference of 4.0 or more)

          When the official CVSS and the AI rating differ by 4.0 or more, the item is flagged for a person to review. The flag does not change the score. Possible reasons: a worst-case default CVSS on a new record, an official score that understates practical impact, or an AI rating that is wrong. Items without an official CVSS (including all CISA KEV entries) are not checked.

          Concurrent Link Health & Scalability Engine

          Active Engine

          High-speed validation architecture designed to verify hundreds of NVD references, forum links, and PoC repositories without bottlenecking the dashboard.

          Why Sequential Checking is Slow & How This Architecture Fixes It:
          1. Checked in parallel

          Checking links one at a time means waiting for every round-trip in turn. The checker runs up to 30 requests at once, with at most 6 to any one site so it doesn't trip rate limits, and it respects Retry-After.

          2. Lightweight requests

          Each link is first checked with a HEAD request, which fetches only the headers. Many servers mishandle HEAD, so a failure is confirmed with a small GET before the link is marked broken.

          3. Cached by result

          Results are stored in link_health_cache.json. Working and blocked links are re-checked after 12 hours, broken or moved links after 6 hours, and temporary errors after 30 minutes. A link that hits a temporary error on two runs in a row is marked broken, and an archive.org copy is looked up for broken or moved links.

          4. Checked before every digest

          The daily pipeline checks every reference before the Telegram digest, so page loads never wait on the network. The digest swaps a broken or moved link for its archived copy, or leaves it out.
